# Troubleshooting

Start by running the local safety check, then the Notes reachability check. Keep
reports sanitized: note titles, text, identifiers, account names, folder names,
operation records, and full local paths can all be private.

## The plugin does not appear

1. Confirm the marketplace source:

   ```sh
   codex plugin marketplace list
   ```

2. Confirm the repository contains `.agents/plugins/marketplace.json` and the
   plugin contains `.codex-plugin/plugin.json`.
3. Restart the ChatGPT desktop app after adding or upgrading a marketplace.
4. Open a new task after enabling the plugin; an existing task may retain its
   prior tool set.
5. If using a local checkout, confirm the marketplace path is absolute and still
   exists.

## `node` is not found or the server fails to start

In Terminal, run:

```sh
node --version
command -v node
```

Guarded Notes MCP requires Node.js 22 or newer. A desktop application can have a
different `PATH` from an interactive shell, particularly with shell-only version
managers. Install a supported Node version in a location visible to desktop
applications, then restart the app.

Run the self-test from the repository to separate Node/plugin problems from
Notes permission problems:

```sh
node plugins/guarded-notes-mcp/tests/self-test.mjs
```

The self-test does not access a live Notes library.

## macOS denies Notes access

The first Notes call may ask whether Node or the host application can control
Notes. Approve Automation access only.

If permission was denied or revoked:

1. Open **System Settings > Privacy & Security > Automation**.
2. Find Node or the host application.
3. Enable its Notes permission.
4. Restart the MCP client and retry `personal_notes_status`.

Do not grant Full Disk Access. This server does not use the Notes database.

## Notes is unavailable or an automation call times out

- Open Notes.app and confirm it is responsive.
- Wait for account synchronization to settle.
- Retry the same bounded operation once.
- Prefer `personal_notes_prepare_organization` for a large library; it adapts
  content and metadata batch sizes when Notes is slow.
- Do not start duplicate background jobs while one reports `running`.
- If one note is consistently unreadable, continue with the reported per-note
  error rather than weakening the content or lock checks.

The MCP tool timeout is five minutes, but individual automation calls have their
own shorter bounds. Apply additionally has a 225-second batch-wide mutation
deadline. If a mutation call times out, its outcome is `uncertain` because Notes
may have completed it; later items are not attempted.

## An inventory is not ready for a snapshot

`personal_notes_export_snapshot` requires a complete sequential inventory for
the exact account in the current connector session.

Either:

- use `personal_notes_prepare_organization`, which creates its snapshot
  automatically; or
- call `personal_notes_inventory` at offset `0` and follow every `nextOffset`
  until it returns `null`, without changing account or folder scope.

A completed inventory is retained in memory for up to two hours and is lost when
the connector restarts.

## A background organization job was interrupted

Organization job status is persisted. If the connector restarts while a job is
running, the restored job is marked failed with phase `interrupted`. Start a new
organization job for the same exact account. Previously committed incremental
cache entries can still be reused.

The simpler `personal_notes_prepare_review` workflow is memory-only and cannot be
resumed after restart.

Background preparation also fails if an apply batch starts or the persisted
mutation epoch changes before its snapshot and manifest are safely published.
Start a fresh organization job after the apply has finished. Failed jobs do not
advertise their unpublished snapshot or manifest.

## A manifest is omitted or complete mode is rejected

`personal_notes_organization_status` defaults `includeManifest` to `false`. Once
the job is ready, call `personal_notes_get_organization_manifest` without a
`mode` to use the bounded default, `next`. Its default page is 100 records and
the maximum is 200.

An embedded or `complete` manifest is allowed only when it has at most 200 notes
and the serialized response is approximately 1 MB or smaller. Use `mode: next`
when either cap is exceeded.

## A cached `contentRef` is unavailable

The referenced private content file may have been moved, deleted, or generated by
a different local data directory. Start a new organization job for the exact
account. Use `forceFull: true` if the cache itself is inconsistent.

Do not manually invent or edit a `personal-notes-content://` reference.

## A snapshot is missing or older than 24 hours

Create a new metadata inventory and snapshot. Snapshot expiration only prevents
new writes; it does not delete the old file.

Do not edit a snapshot timestamp. The purpose of the age check is to require a
recent view of Notes before planning changes.

If `includeContent: true` is rejected, use a metadata-only snapshot. A content
snapshot is limited to 100 readable notes and 50,000 characters for each stored
HTML and plaintext field.

## A plan token is unknown or expired

Plans are kept only in the running server process, can be used once, and expire
after ten minutes. A restart also invalidates them.

Generate and review a new plan. Never try to reconstruct a token from the digest
or operation history.

## The confirmation phrase is rejected

Copy the exact phrase returned with the same plan. Capitalization, spaces, action
kind, move/folder counts, and bracketed uppercase digest prefix must match. The
shape is `APPLY n MOVES + n FOLDERS [DIGESTPREFIX]`, or `ROLLBACK` for a rollback.
Do not reuse a phrase from another plan.

## The move safety lock is missing, invalid, or expired

Run the command returned by `personal_notes_safety` or the plan in an interactive
Terminal. Paste the exact 32-character plan token and exact 64-character
lowercase hexadecimal plan digest, then type that plan's exact digest-suffixed
confirmation phrase. An authorization:

- expires after ten minutes;
- is bound to that token, full digest, and phrase;
- is consumed before the first write;
- authorizes only one apply attempt; and
- cannot be created through an MCP tool.

Remove an unused authorization with the bundled disarm script. If an expired or
malformed authorization remains, disarm and create a new one.

## Another apply batch or a mutation-lock record blocks changes

Only one apply batch may own the owner-only `mutation.lock` across all Guarded
Notes MCP server processes. Wait for a known batch to finish. A structurally
valid lock whose recorded process is no longer alive is recovered conservatively
on a later attempt.

Unreadable, malformed, conflicting, or apparently live lock/recovery records fail
closed. PID reuse can make an abandoned record appear live. If no batch is known
to be running:

1. Quit every MCP client or plugin process that can run Guarded Notes MCP.
2. Inspect Notes and the relevant `Operations/` journal before changing local
   safety files; an `in-progress` item has an uncertain outcome.
3. In Activity Monitor, confirm that the PID recorded in the lock is not a live
   Guarded Notes MCP process.
4. Preserve a copy, then use Finder to move only the exact `mutation.lock` and
   associated `mutation.lock.recovery-*` records out of the Application Support
   directory.
5. Restart the client and prepare a fresh inventory, snapshot, and plan.

There is no automatic inference of a mutation's outcome after a crash. If the
lock ownership is unclear, stop and request support with sanitized metadata.

## The persisted mutation epoch is unreadable

`mutation-epoch.json` protects background snapshot and manifest publication from
concurrent writes. An unreadable or malformed record fails closed. Quit all
Guarded Notes MCP processes, preserve the file for diagnosis, inspect any recent
operation journal and Notes state, then move only that epoch file aside and start
a fresh preparation job. Do not reuse a snapshot or plan from before recovery.

## A note or destination is blocked

The planner deliberately rejects:

- locked or shared notes;
- shared source or destination folders;
- cross-account moves;
- nested source folders;
- missing or ambiguous destinations;
- protected system names;
- duplicate notes or folder requests; and
- notes already in the destination.

Change the proposed organization rather than bypassing the restriction. Some
cases can be handled manually in Notes after independent review.

## Only part of a batch succeeded

Do not rerun the original apply request. Its plan token and one-use authorization
have already been consumed.

1. Save the returned `operationId`.
2. Review the batch status and each folder/note state: `succeeded`, `failed`,
   `uncertain`, or `not-attempted`. Treat a lingering `in-progress` journal state
   as uncertain.
3. Inspect current state in Notes.
4. Prepare a fresh inventory and snapshot.
5. Either create a new forward plan for remaining notes or prepare a rollback for
   successful moves.

An empty folder created during the partial batch may remain. Guarded Notes MCP
does not delete folders.

The apply journal is written before the first mutation and replaced after every
state transition. A batch may finish `completed`, `partial`, or `interrupted`.
The 225-second deadline can produce a valid `partial` result with later items
`not-attempted`; an Automation timeout produces an `interrupted` result with the
current item `uncertain`.

## A title-and-content search reports truncation

The content phase intentionally stops at 500 candidate notes, 50,000 characters
per note, or 10,000,000 characters overall. It also stops once the requested
result limit is satisfied. If `contentSearchTruncated` is true, a non-match is not
proof that no later or truncated body contains the query. Narrow the account or
query, use title search, or inspect selected notes explicitly.

## Local data uses unexpected disk space

Organization content, manifests, snapshots, jobs, and operation records are not
automatically purged. Quit the MCP client, open Finder, and review:

```text
~/Library/Application Support/Guarded Notes MCP/
```

Moving `Cache/`, `Content/`, `Jobs/`, and `Manifests/` to Trash removes local
review state without changing Notes. Removing `Snapshots/` and `Operations/`
also removes the metadata needed for recent write plans and rollback planning.

## Reporting a reproducible problem

Follow [Support](../SUPPORT.md). Include only:

- Guarded Notes MCP version;
- macOS and Node major versions;
- installation method;
- tool name and workflow phase;
- exact error with private values replaced by placeholders; and
- minimal reproduction steps using synthetic notes.

For a vulnerability, do not open a public issue. Follow
[SECURITY.md](../SECURITY.md).
